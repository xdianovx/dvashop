# DvaShop

Laravel 13 Blade-монолит для интернет-магазина автотоваров.

Текущий рабочий фокус проекта: backend, Filament-админка, каталог, импорт Excel/CSV, обработка изображений, очереди и storage hygiene. Публичную Blade-вёрстку магазина на этом этапе не развиваем и не меняем без отдельной задачи.

## Что уже есть

- Docker-окружение для Laravel, MySQL, Redis, очередей, scheduler, Vite, Mailpit и Adminer.
- Web/session-авторизация и Filament-админка `/admin`.
- Простые роли пользователей: `super_admin`, `admin`, `manager`, `customer`.
- Модели каталога: категории товаров, марки, модели, поколения авто, товары, варианты, изображения и применимость.
- Заказы, корзина и базовая checkout-логика в backend.
- Импорт каталога из CSV/XLSX через Filament.
- Очереди для строк импорта и удалённых изображений.
- Media pipeline: загрузка, валидация, конвертация в WebP, conversions, дедупликация и cleanup старых файлов.

## Сервисы Docker

`docker-compose.yml` поднимает:

- `app` — PHP-FPM 8.4, Laravel-приложение;
- `nginx` — web-сервер; Compose fallback — `8080`, а `.env.docker.example` использует менее конфликтный `8088`;
- `mysql` — MySQL 8.4, порт хоста по умолчанию `33066`;
- `redis` — Redis 7, порт хоста по умолчанию `63790`;
- `queue` — `php artisan queue:work`;
- `scheduler` — `php artisan schedule:run` каждую минуту;
- `node` — Vite dev-server, порт по умолчанию `5173`, запускается только через профиль `frontend`;
- `mailpit` — локальная почта, web-интерфейс `8025`;
- `adminer` — web-интерфейс к БД, порт `8081`.

`queue` и `scheduler` ждут появления `vendor/autoload.php`, поэтому первый запуск до `composer install` не валит окружение постоянными PHP-ошибками.

## Первый запуск в Docker

Локальный `.env` создаётся вручную из примера и никогда не хранится в репозитории или clean-архивах:

```bash
cp .env.docker.example .env
```

Пример использует `APP_PORT=8088`, чтобы не конфликтовать с другими локальными проектами на `8080`. При необходимости выбери свободный порт в своём `.env`; Compose fallback остаётся `8080`.

Перед миграциями поменяй в `.env` данные первого администратора:

```dotenv
ADMIN_NAME="DvaShop Super Admin"
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=change-me
```

Запуск контейнеров:

```bash
docker compose up -d --build
```

Обычный запуск поднимает backend-сервисы без Vite и не создаёт `public/hot`. Для frontend-разработки запусти профиль явно:

```bash
docker compose --profile frontend up -d node
```

После остановки Vite файл `public/hot` удаляется автоматически:

```bash
docker compose --profile frontend stop node
```

Установка PHP-зависимостей:

```bash
docker compose exec app composer install
```

Если `composer.lock` еще не обновлен после добавления Filament, один раз выполни:

```bash
docker compose exec app composer update filament/filament --with-dependencies
```

Ключ приложения:

```bash
docker compose exec app php artisan key:generate
```

Storage link создаётся локально и не коммитится:

```bash
docker compose exec app php artisan storage:link
```

Миграции и сидер первого `super_admin`:

```bash
docker compose exec app php artisan migrate --seed
```

Сборка фронтенда:

```bash
docker compose --profile frontend run --rm node npm install
docker compose --profile frontend run --rm node npm run build
```

Одноразовый интерактивный запуск Vite:

```bash
docker compose --profile frontend run --rm --service-ports node npm run dev -- --host 0.0.0.0
```

Тесты:

```bash
docker compose exec app php artisan test
```

## Админка

Админ-панель доступна по адресу:

```text
/admin
```

Используется стандартный Laravel `web` guard на сессиях. Passport и API-авторизация не подключались.

Роли пользователей хранятся простым полем `users.role`:

- `super_admin`;
- `admin`;
- `manager`;
- `customer`.

В админку допускаются `super_admin`, `admin`, `manager`. `customer` остается обычным клиентским пользователем без доступа к `/admin`.

Первый `super_admin` создается сидером `Database\Seeders\AdminUserSeeder` из переменных окружения `ADMIN_NAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`.

## Проверка после запуска

```bash
curl -I http://localhost:8088/
curl -I http://localhost:8088/admin
```

Ожидаемо:

- `/` отвечает `200`;
- `/admin` для гостя редиректит на страницу входа Filament;
- пользователь с ролью `super_admin` входит в админку.

## Импорт каталога

Инфраструктура импорта доступна в Filament-админке:

```text
/admin/imports/catalog
```

Импорт синхронизирует ассортимент одного источника. Всегда читается **первый лист** XLSX; имя файла/листа не определяет поведение. Ошибка первого листа не разрешает переходить ко второму. Режима «дополнение» больше нет.

Схема: две строки заголовков. Обязательны именованные колонки «Марка», «Модель», «Поколение», «Годы выпуска» (также «Годы»), «Кузов». Дополнительно распознаются «Платформа», «Рестайлинг», «Ссылка на фото автомобиля» (также «Фото»). Колонки можно переставлять. Если фото-колонок несколько, выбирается первая непустая слева направо. Остальные именованные колонки — детали; группа задаётся реальным объединением ячеек первой строки либо явным путём `Группа / Деталь`. Пустой заголовок с заполненными ячейками и коллизии нормализованных путей запрещены.

Значения деталей:

- Число `1` или текстовое представление единицы (`1`, `1.0`, `1,0`, с допустимыми внешними пробелами): товар присутствует.
- `0`, пустая ячейка и любое другое значение (`maver`, `abc`, `да`, другие числа, ссылки): товар отсутствует. Такие значения не являются ошибкой файла и не задают цену или изображение товара.
- Служебные колонки, включая ссылки на фото автомобиля, обрабатываются отдельно. Проверки структуры, обязательных идентификаторов и коллизий сохраняются. Защита от полностью пустого снимка остаётся прежней.

Ключ товара строится прежним `CatalogText::stableKey` из источника, нормализованных марки/модели/поколения (годы, кузов, платформа, при наличии рестайлинг) и структурного пути детали. Это сохраняет совместимость со старой БД. Точные нормализованные совпадения старых поколений сохраняют их прежние ключи; неоднозначности запрещены. Регистр/пробелы и запись количества дверей нормализуются. Переименования марок, моделей и типов без неизменяемого ID нельзя надёжно распознать: старая идентичность архивируется, новая создаётся. Алиасов конкретных марок и fuzzy matching нет. Существующие slug сохраняются.

Обработка:

1. Проверить системный шаблон (4 группы, 9 активных значений, 24 комбинации), заголовки и **весь** файл. Подготовить JSONL со смещениями, чтобы задания очереди не разбирали Excel заново.
2. Разрешить типы/категории через существующие справочники. Новый произвольный тип использует общую резервную категорию; отсутствие магазинных prerequisites останавливает запуск.
3. Записать ожидаемые уникальные ключи в `catalog_import_snapshot_items`. Повторные строки одного автомобиля объединяют отмеченные позиции; конфликтующие цены и коллизии запрещены.
4. Обработать строки порциями. Новые карточки и поколения до публикации скрыты. Существующие статусы, ID, URL, ручные данные и варианты сохраняются. По каждому ожидаемому ключу фиксируется обработанная карточка.
5. После всех строк, без ошибок, под блокировкой запуска сверить полный набор. В одной транзакции активировать присутствующие, архивировать отсутствующие товары этого источника и скрыть отсутствующие импортные поколения без активных товаров. Ручные/другие источники защищены. Неатрибутируемые старые автомобили без товаров не считаются собственностью импортера.
6. В той же транзакции зафиксировать завершение строк. После commit обновить поиск; фотографии завершаются отдельной очередью.

При сбое активный ассортимент остаётся последним применённым снимком. Уже записанные импортируемые названия/связи/метаданные и обработанные фото могут обновиться до финальной публикации: откат всего содержания каталога не обещается. Новые недоприменённые карточки остаются архивными и переиспользуются при повторной загрузке. Пауза/продолжение и повтор задания сохраняют прогресс; после терминальной ошибки файл загружается заново. Старые подготовленные additive-запуски нужно отменить и загрузить повторно. Старты и чанки одного источника используют общую блокировку; финализация также блокирует запись запуска в БД.

Цены новых карточек берутся из утверждённого справочника, а не из значений наличия. Существующие ручные цены, изображения/главное фото, SEO, описания, характеристики, SKU и остатки не перезаписываются. Неизменившиеся скачанные изображения не загружаются повторно.

Поиск после snapshot-импорта публикуется независимо от изображений: запрос в `catalog_search_publications` записывается в той же транзакции, что активация/архивация. После коммита `PublishCatalogSearch` в существующей очереди `catalog-search` обновляет документы пакетами по `scout.chunk.searchable`. Курсор сохраняется только после подтверждения `succeeded` от Meilisearch; сбой повторяет незавершённый пакет. Архивные документы получают `is_active = false`, существующий фильтр поиска исключает их. Загрузка фото и переход snapshot-импорта в `Done` не запускают повторную полную индексацию.

Планировщик каждую минуту проверяет незавершённые запросы поиска; потерянное задание или исчерпанные попытки возвращаются в очередь после 15-минутной аренды. Завершённые запросы не выполняются повторно, публикации обрабатываются по порядку. Нужны работающие scheduler и worker `catalog-search`. До применения миграции `2026_10_12_000100_create_catalog_search_publications` планировщик безопасно пропускает эту проверку. Миграция требует отдельного подтверждения для рабочей БД. Обновление поиска асинхронное, пакетное, без обещания атомарной смены всех поисковых индексов; запрос остаётся незавершённым до подтверждения всех пакетов.

Очереди: `imports` и `imports-images`. Миграция `2026_10_09_000100_create_catalog_import_snapshot_items` добавляет только служебную таблицу и nullable-поле цены; существующие товары/варианты не переписывает. На рабочей БД запускать миграции только после отдельного подтверждения. Исправление `default_auto_part` и его безопасная миграция предыдущего этапа сохраняются.

Диагностика без записи в БД: `php artisan import:inspect-file <path>`. В первом листе `auto_base_new.xlsx` значение M1326 (`maver`) означает отсутствие товара. Тесты подготовки и полного импорта запускаются с `CATALOG_IMPORT_NEW_FIXTURE`, указывающим на исходный XLSX без исправлений. Ожидаемый ассортимент вычисляется по фактическим единицам первого листа. Полный тест проверяет legacy-карточки и повторный импорт; пропуск не считается успешным прогоном. HTTP в полном тесте подменён, изображения проверяются отдельно.

## Media storage and image processing

Public images are stored on the `public` filesystem disk. Import source files are stored on the local private disk under `storage/app/imports/...` and are downloaded only through Filament actions.

Storage link:

```bash
php artisan storage:link
```

`public/storage` создаётся только этой командой и не должен попадать в git или clean-архив.

Image uploads and import downloads use the shared media pipeline:

- product images: `uploads/products/{product_id}/{uuid}.webp`
- product conversions: `uploads/products/{product_id}/conversions/{uuid}_thumb.webp`, `..._card.webp`
- vehicle generation images: `uploads/vehicles/generations/{generation_id}/{uuid}.webp`
- vehicle make images: `uploads/vehicles/makes/{make_id}/{uuid}.webp`

Supported source formats are JPEG, PNG and WebP. Non-images, SVG, PDF and HTML responses are rejected. The default source file limit is configured in `config/media.php` and can be overridden with `MEDIA_MAX_SOURCE_SIZE`.

The local PHP image must have GD with WebP support. After Dockerfile changes rebuild the app container before running image tests:

```bash
docker compose build app
docker compose up -d
docker compose exec app php -r "var_dump(extension_loaded('gd'), function_exists('imagewebp'));"
```

## Clean archive hygiene

Локальная разработка может иметь `.env`, `public/storage`, логи, cache, sessions и build-файлы. Но git и clean-архив не должны их содержать.

Проверка tracked-файлов и обязательной структуры:

```bash
php artisan project:check-clean-tree
```

Строгая проверка физического clean-tree перед ручной упаковкой:

```bash
php artisan project:check-clean-tree --strict
```

Перед созданием clean-архива нельзя передавать:

- `.env`, `.env.*`, кроме `.env.example`, `.env.docker.example` и `.env.testing.example`;
- `public/storage`;
- `public/hot`;
- `bootstrap/cache/*.php`;
- `vendor`;
- `node_modules`;
- `*.patch`;
- `*.tar.gz`, `*.tgz`, `*.zip`;
- `*:Zone.Identifier`;
- реальные файлы внутри `storage/app/imports`, `storage/app/public`, `storage/logs`, `storage/framework/cache`, `storage/framework/sessions`, `storage/framework/views`.

Создать clean-архив из tracked-файлов git можно скриптом:

```bash
scripts/make-clean-archive.sh ../dvashop_clean_$(date +%Y%m%d_%H%M%S).tar.gz
```

Скрипт использует `git archive`, проверяет hygiene через `project:check-clean-tree`, затем дополнительно проверяет содержимое созданного архива. `.env.example`, `.env.docker.example`, `.env.testing.example`, `storage/**/.gitignore` и `bootstrap/cache/.gitignore` остаются в архиве.

## Изолированная проверка миграций и сидеров

`php artisan test` уже использует SQLite `:memory:` через `phpunit.xml`. Для отдельного запуска `migrate:fresh --seed` подготовлен безопасный файловый SQLite-конфиг:

```bash
cp .env.testing.example .env.testing
docker compose exec app sh -lc 'touch /tmp/dvashop_testing.sqlite && chmod 600 /tmp/dvashop_testing.sqlite'
docker compose exec \
  -e APP_ENV=testing \
  -e DB_CONNECTION=sqlite \
  -e DB_DATABASE=/tmp/dvashop_testing.sqlite \
  -e DB_URL= \
  -e CACHE_STORE=array \
  -e QUEUE_CONNECTION=sync \
  -e MAIL_MAILER=array \
  -e SESSION_DRIVER=array \
  app php artisan migrate:fresh --seed --env=testing --force
```

Явные `-e` нужны в Docker, потому что Compose передаёт значения рабочего `.env` контейнеру. Они гарантируют, что destructive-команда работает только с `/tmp/dvashop_testing.sqlite`, а не с dev MySQL. Реальный `.env.testing` игнорируется Git и не должен коммититься.

### Массовое изменение цен автодеталей

После миграции `2026_10_13_000100_add_catalog_pricing` функция доступна в админке:
**Каталог → Массовое изменение цен**. Нужны оба разрешения: изменение товаров и изменение каталога.

- `part_types.base_price` — актуальная цена конкретного типа (DECIMAL). Родительская область включает потомков через дерево типов; автоматического поиска цены у предка нет.
- `products.price_mode` и `product_variants.price_mode`: `inherited`, `individual`, `unknown`. Товар наследует цену типа, вариант — цену своего товара. Старые записи получают `unknown`; сравнение с `last_import_price` не считается доказательством наследования.
- Миграция переносит известные справочные цены только в типы. Цены существующих товаров и вариантов не изменяются. Seeder заполняет только отсутствующие базовые цены; импорт читает исключительно БД.
- Предпросмотр ничего не записывает. Решения по исключениям автоматически пересчитывают итог; изменение типа, области или новой цены требует нового расчёта. Перед подтверждением область перечитывается, а отпечаток цен, режимов, состава и решений сравнивается с показанным. Старые открытые редакторы товаров также защищены от перезаписи новых цен.
- «Сохранить исключения» оставляет индивидуальные/исторические цены; зависимые цены наследующего товара обновляются. «Заменить общей» явно выравнивает всю карточку и все варианты, включая защищённые.
- Операция и её решения сохраняются в `catalog_price_operations`. Пакеты по 100 товаров записывают цены и курсор одной транзакцией. `catalog_price_overrides` содержит перезаписанные карточки и прежние цены вариантов. Повтор задания продолжает с курсора, завершённое задание ничего не меняет.
- Очередь использует существующее подключение и очередь по умолчанию. Планировщик раз в минуту восстанавливает потерянную постановку задания после истечения пятиминутной аренды. Необходимы работающие worker и scheduler. Кнопка «Продолжить обработку» повторно ставит незавершённую операцию; уже применённые пакеты не откатываются.
- Пока операция не завершена, конфликтующее изменение цен/структуры и запуск/возобновление Excel заблокированы. Остатки и загрузка фотографий независимы. Обновление цен видно на витрине по мере применения пакетов; Yandex-feed публикуется после завершения, с повторяемым уведомлением. Полная переиндексация Meilisearch не запускается.
- Новые импортные товары получают текущую базовую цену и наследующие варианты. Тип без базовой цены требует назначения цены администратором; импорт не изобретает её. Повторный импорт и реактивация сохраняют назначенные режимы и цены.

Перед внедрением: проверить изменения, сделать штатную резервную копию БД, завершить активные импорты, применить согласованные миграции в окно обслуживания и перезапустить workers. Сначала проверить предпросмотр одного типа и исторические исключения, затем отдельно подтвердить небольшую операцию. Большие области требуют полного чтения выбранных цен при просмотре и повторной проверке; подтверждение удерживает блокировку записи цен на время сверки. Нагрузочная проверка ниже выполнена на отдельном MySQL 8.4. Рабочая БД при разработке этой функции не изменялась.


#### Первоначальное принятие исторических цен и восстановление

На странице цен выберите режим **«Принятие исторических цен»**, конкретный тип и нажмите **«Проанализировать исторические цены»**. Новую цену для анализа вводить не требуется. Будет предложена сохранённая база, а при её отсутствии — наиболее распространённая цена. Это только предложение: до подтверждения БД не изменяется. Анализ показывает распределение цен, совпадения, отклонения, несовпадающие варианты, явные индивидуальные цены и недостаточные данные. `last_import_price` и `old_price` учитываются в проверке версии и диагностике, но не доказывают источник цены.

Режим принятия работает для одного конкретного типа и **не изменяет суммы**. В наследование переходят только неизвестные режимы карточек, у которых основная цена и все варианты совпадают с подтверждённой базой, без явно индивидуальных вариантов. Отсутствие вариантов считается недостатком данных. Отклонения по умолчанию остаются историческими; можно массово или по отдельным строкам отметить неизвестные режимы как индивидуальные. Явно установленные режимы защищены. Решения действуют на всю выборку, а не на страницу. Повторное принятие не создаёт изменений. Если уже наследуемые цены расходятся с выбранной базой, сначала требуется обычное изменение общей цены.

После принятия используйте обычное массовое изменение. Исторические и индивидуальные исключения сохраняются, даже если численно совпадают с базой. Принудительное выравнивание всей карточки требует отдельного подтверждения. Старые цены и режимы изменённых карточек/вариантов сохраняются в журнале `catalog_price_overrides`; исходный состав и отпечатки — в `catalog_price_items`.

Перед каждым пакетом под блокировкой повторно сверяются исходные цены, зачёркнутые цены, режимы, варианты, типы и состав выборки. Конфликт переводит операцию в «Требует внимания» до отмены остатка и нового просмотра. Запоздавшее задание привязано к исходному курсору и не обрабатывает следующий пакет. Пакет и его аудит/курсор фиксируются одной транзакцией, с тремя попытками при deadlock.

Статусы: ожидание, выполнение, завершение, требует внимания, ошибка, отменён остаток. После трёх неудачных попыток/потерь доставки одного пакета операция завершается с ошибкой и освобождает блокировку. Временные сбои восстанавливает очередь/планировщик. «Продолжить» доступно после устранения причины, если не начата более новая операция или импорт; сохранённые отпечатки снова проверяются. «Отменить остаток» сохраняет уже записанные пакеты и базу, освобождает каталог; полного отката нет. Поэтому при частичной остановке цены могут временно различаться. Завершение, окончательная ошибка и отмена запускают повторяемое уведомление Yandex-feed о фактически сохранённых ценах.

`old_price` — зачёркнутая цена. Массовые операции сохраняют исходные значения; витрина, матрица вариантов и Yandex-feed показывают их только при положительной текущей цене и `old_price > effectivePrice`. Равная или меньшая зачёркнутая цена скрывается. В административном редактировании/исторических данных исходное значение остаётся доступным.

Проверка схемы цен кэшируется только на время запроса/задания, отдельно для каждого объекта соединения, и сбрасывается при DDL. Запроса `Schema::hasColumn()` на каждое сохранение больше нет. После применения миграций обязательно перезапустить долгоживущие workers.

Старый объединённый тип усилителя/соединителя не переназначается: его карточки архивируются
обычной сверкой Excel и могут вернуться с прежними ключами при возвращении старой колонки.

В `/admin/catalog/prices` вкладка «Статусы товаров и конфигурации» позволяет выбрать тип,
подтипы и исходный статус, получить предпросмотр, затем подтвердить пакетную операцию:

- применение конфигураций: совпадающие варианты сохраняют ID, индивидуальные и исторические цены; общие цены
  берутся из матрицы. Старые неподходящие
  варианты становятся неактивными, связи с заказами сохраняются; недостающие создаются;
- цена одной конфигурации: меняется матрица и только наследующие эту цену варианты;
  индивидуальные и исторические цены защищены;
- активен / архив / черновик: цены и варианты не меняются. Ручной архив/черновик сохраняются
  при новых Excel-импортах. Обычная активация снимает ручное скрытие, но не публикует отсутствующий
  в Excel товар; принудительная публикация требует отдельного явного флага в предпросмотре.

Пользовательские шаблоны не заменяются автоматически. Повторные строки автомобиля
объединяются по наличию: хотя бы одна единица означает присутствие детали. Неизвестные
значения, в том числе `maver`, означают отсутствие; структурные коллизии по-прежнему запрещены.

Операция резервирует каталог, сохраняет состав выборки и исходные состояния, обрабатывает
по 100 товаров в транзакции. Повторная доставка уже обработанного пакета безопасна.
Изменение данных после предпросмотра требует нового расчёта. Ошибка приостанавливает
операцию с сохранением курсора; «Продолжить» возобновляет её, «Отменить остаток» сохраняет
уже выполненные изменения. Журнал и исходные значения находятся в `catalog_actions` /
`catalog_action_items`. После завершения публикуются только затронутые товары; курсор
публикации движется после подтверждения Meilisearch. Недоставленные задания восстанавливает
ежеминутный `catalog-actions-recovery`. Должны работать обычные queue worker и scheduler.

#### Последовательное применение оставшихся типов без ручных подтверждений каждой группы

После проверки двух контрольных типов можно применить оставшиеся через штатную команду
`catalog:configurations-remaining`. Без `--apply` команда только читает рабочую локальную
БД, показывает состав оставшихся типов, числа вариантов и выдаёт токен предпросмотра:

```bash
php artisan catalog:configurations-remaining
```

После проверки цифр и наличия резервной копии оператор вручную запускает напечатанную
команду с `--apply --confirm=<токен>`. Команда допускает только локальную MySQL `dvashop`,
требует действующего суперадминистратора, свободного каталога и завершённых импортов.
Она подтверждает каждую операцию через `CatalogActions`, ждёт штатную очередь и публикацию,
после каждого типа требует повторный предпросмотр с нулём изменений и останавливается при
ошибке, паузе или устаревшем подтверждении. Уже синхронизированные типы пропускаются.
При остановке нельзя слепо повторять `--apply`: сначала проверить журнал операций.

Безопасный порядок применения (не выполняется автоматически):

1. Независимая проверка изменений, резервная копия рабочей базы и проверка восстановления.
2. Завершить текущие импорты/массовые операции; развернуть код, применить аддитивные миграции
   и перезапустить долгоживущие обработчики очередей.
3. Проверить актуальный CSV командой без `--apply`, затем отдельно установить определения.
4. В админке проверить предпросмотр конфигураций по типам, защищённые товары и объём
   создаваемых/выводимых из продажи вариантов. Применять небольшими областями, проверяя
   витрину, цены и журнал. Исторические неизвестные цены намеренно не заменяются CSV-ценами.
5. После согласования выполнить актуальный Excel-импорт и проверить итоговый снимок,
   архив старого объединённого типа, поисковую публикацию и Yandex-feed.
6. Проверить повторный импорт, корзину и заказ на согласованных тестовых карточках.

Проверки разработки выполняются только в изолированных БД. Полный XLSX-тест включается
переменной `CATALOG_CONFIGURATION_XLSX` с путём к исходному файлу внутри тестового контейнера.
`tests/Performance/catalog-configurations-mysql.php` отказывается работать вне отдельного
пустого `dvashop-config-mysql-test` / `dvashop_config_test` на MySQL 8.4; он не использует
рабочие реквизиты или рабочие тома. Сам исходный Excel тесты не редактируют.


#### Повторная установка конфигурационного CSV

Перед `--apply` команда `catalog:configurations /path/config.csv` выводит добавляемые,
отключаемые и возвращаемые комбинации, расхождения цен и код `confirmation`. Изменение
существующего набора или конфликт цен требует `--apply --confirm=<код>` именно этого
предпросмотра. При изменении CSV или матрицы код устаревает, операция отклоняется целиком.
Удалённые комбинации (включая полностью удалённую группу CSV) становятся неактивными;
возвращённые получают прежний ID. Удаления вариантов и изменения снимков заказов нет.
Существующая цена сохраняется даже после подтверждения: сменить её можно отдельным
массовым действием цены конфигурации. Поэтому повторное применение CSV при расхождении
с административной ценой снова требует подтверждения сохранения этой цены.

Установка определений по-прежнему отделена от пакетного применения к карточкам.
Предпросмотр применения сравнивает реальные варианты, связи, цены, названия, опции,
шаблон и выбор по умолчанию; повторное применение без изменений показывает ноль.
Новые варианты содержат название конфигурации и снимок опций. При исправлении ранее
созданных вариантов заполняются только отсутствующие названия/опции; исторические
позиции заказов остаются неизменными.

`tests/Performance/catalog-configurations-real-catalog.php` проверяет переход на копии
реального каталога, восстановленной потоковым `mysqldump --single-transaction
--skip-lock-tables --no-tablespaces --set-gtid-purged=OFF` в отдельную MySQL 8.4.
Скрипт жёстко ограничен хостом `dvashop-config-audit-test` и базой `dvashop_audit_test`,
отключает реальные очереди, поиск, почту и внешние HTTP-запросы. Фаза `prepare` сохраняет
контрольные данные внутри тестовой БД, применяет миграцию и конфигурации; `configurations`
позволяет продолжить обработку; `import` выполняет два прохода актуального Excel.
Сравниваются старые ID, URL, защищённые цены и полные контрольные суммы заказов/позиций.
Рабочая БД используется только как источник чтения для первоначального копирования.
